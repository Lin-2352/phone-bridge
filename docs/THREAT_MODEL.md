# Relay: threat model

No external review yet. Update whenever a feature adds a new trust boundary.

## What we protect
| Asset | Why it matters |
|---|---|
| Clipboard contents | Often passwords, tokens, personal text |
| Files in transit | Arbitrary private data |
| Input control of the phone | Remote control of an unlocked phone is full account takeover |
| Camera and microphone streams | Live surveillance if hijacked |
| Phone notifications | Message text, senders, one-time codes; acting on them (reply, answer a call) speaks for the user |
| The phone's screen | Everything on it, live; input from the window acts on the unlocked phone |
| Device identity keys | Whoever holds one can impersonate the device |
| Metadata (who pairs with whom, when, from where) | Location and relationship leakage |

## Actors
- **Owner**: the user, with both devices.
- **Network attacker**: on the same Wi-Fi, or controlling a router/ISP/relay. Can read, drop, modify and inject packets. Cannot break standard cryptography.
- **Nearby attacker**: within BLE/Wi-Fi range, can broadcast discovery packets and attempt pairing.
- **Malicious relay operator**: sees connection metadata (IPs, timing, sizes) of anyone using their relay. Must never see content.
- **Malicious app on the same device**: another app trying to read clipboard, abuse the accessibility service, or talk to our local sockets.
- **Thief with the unlocked or locked device**: physical access.

Out of scope (for now): a fully compromised OS or kernel, hardware attacks, nation-state targeted malware on an endpoint, supply-chain compromise of the Rust toolchain.

## Trust boundaries and main threats
| # | Boundary | Threat | Mitigation (status) |
|---|---|---|---|
| 1 | Pairing | Man in the middle during first contact; a paired or pasted peer planting extra store entries | QR bootstrap carries the peer public key; 6-digit SAS compared by the user; nonce commitment before reveal. Addresses a peer sends (or a pasted code carries) are kept only when they parse as `ip:port`, at most 6; names lose control and hidden bidi characters and are capped at 64 characters; the store writes one peer per line and refuses lines with extra fields (**implemented** in `pb-transport::pairing` and `pb-identity`, tested; QR rendering still planned) |
| 2 | Pairing | Stranger pairs by guessing or spamming requests | Codes exist only while the host shows one; single use, 2-minute expiry, burned after 3 wrong tokens (**implemented**) |
| 3 | Transport | Eavesdropping or tampering | QUIC with TLS 1.3, peers authenticated by pinned Ed25519 keys (iroh endpoint ids). Only keys in the paired-peer store may open sessions; others are closed with code 403 before any stream is read; revocation takes effect for new connections and closes open ones; a removal or pairing that cannot be saved to disk is reported and changes nothing, so a revoked device cannot come back after a restart (**implemented**, tested in-process and on the real phone) |
| 4 | Discovery | Tracking a device by its broadcasts; planting addresses | No device name in discovery. Probes carry a tag `SHA-256("pb-discovery/1" \|\| peer id \|\| 30-minute window)[..16]`, which changes every 30 minutes but is **not keyed**: anyone who knows a device's public key (for example a formerly paired device) can compute it, ask whether that device is on the LAN and get its IP and QUIC port, or answer with a planted address. Planted addresses are only dial candidates: a connection must still prove the paired key, and only the address an authenticated connection uses is saved (**implemented**; keying the tag with a secret exchanged at pairing is **planned**). From M7.6 (**implemented**): keyed discovery, PBD2, derives a per-pair key from the two paired identities (X25519 over the Ed25519 keys, HKDF-SHA256) and authenticates probes and answers with a 16-byte HMAC over the exact packet, so only a paired device can ask or answer; a replay cache refuses repeats, only MACed addresses become candidates, and probes are padded to at least 4 so the count does not show how many peers are paired. PBD1 stays for peers that have not announced `discovery2` and is removed in the next minor release |
| 5 | Relay | Operator reads content | End-to-end encryption between devices; relay only forwards QUIC packets. Self-hostable relay; default build must not use third-party relays without consent (Spike 1 uses none) |
| 6 | Relay | Operator learns metadata | Cannot be eliminated; documented. Users can self-host. |
| 7 | Clipboard | Silent theft of secrets | Universal Clipboard is opt-in (off by default); private content (Windows exclusion formats, Android `EXTRA_IS_SENSITIVE`) never sent; received sensitive text excluded from Win+V history/cloud; echo guard; the Android clipboard-reading activity is not exported so other apps cannot trigger it (**implemented**) |
| 8 | Files | Path traversal, zip bombs, overwriting files | Names sanitised (last component only, reserved/control chars, Windows device names, length), unique names, partial file + SHA-256 check before rename, 4 GiB cap; auto-accept only from paired devices, otherwise prompt (**implemented**, tests incl. hostile names, forged hash, interrupted sender) |
| 9 | Input control | Hijacking the phone | Paired devices only; explicit session started by the user (touchpad screen, or Ctrl+Alt+P on the PC); PC side gated by a setting, phone side by an accessibility service the user must enable in Android settings (off by default, revocable there at once); visible indicators (toast and cursor on the phone, notification on the PC); held keys and buttons released when a session ends; PC hooks installed only during a session (**implemented**) |
| 10 | Accessibility service | Abuse by other apps or policy loss | The service is part of the single Android build (there are no Gradle flavors; the planned separate `play` build without it was not made). It does nothing until the user enables it in Android's accessibility settings, where it can be turned off at once; no data collection; it acts only inside a session the user started (row 9). A store build that must not carry it would need a flavor first (see DECISIONS.md) |
| 11 | Parsers | Memory corruption or DoS from malformed input | Size limits before allocation, no panics on bad input, fuzz targets (**implemented for control frames, input records and audio datagrams**; fuzzing harness **planned**) |
| 12 | Keys at rest | Theft from disk or backup | Seed wrapped by Android Keystore / Windows DPAPI; excluded from backups (**implemented**: DPAPI on Windows, Keystore AES-GCM on Android; unseal failure is an error, never a silent new identity; Android backup disabled) |
| 13 | Updates | Malicious update | A signed release manifest is verified before the update check offers anything, with rollback, replay and key-rotation rules (row in the M9 to M11 section); the check only opens the release page and installs nothing. **Not yet active:** no public key is embedded until the owner supplies one, so every manifest is refused. The Android APK is signed with the owner's release key; the Windows signing step runs only when a certificate is configured, so releases are unsigned until then. Reproducible builds are not claimed |
| 14 | Resource use | Battery or CPU drain used as DoS | At most 16 incoming handshakes at once (5 s each) and 2 pairing connections from their own pool; input and notification actions are rate-limited per session; control frames 64 KiB. Per paired peer (M7.8): at most 16 sessions open at once (the next is closed with code 429 "busy"), 30 file offers a minute, and an offer plus the peer's other in-flight offers plus a 256 MiB margin must fit in the free space (**implemented in the transport; the tray and ffi call `Node::offer_permit` when an offer arrives, still to be wired: partly implemented**); a wrong pairing token is limited per source (below); idle budget tracked in DECISIONS.md |
| 15 | Phone notifications | Content leaks, forged actions, malformed images | Only to paired peers over the session transport (row 3), and only after the user grants Android Notification access and leaves "Notifications on PC" on. Nothing is stored except toast images (a private temp folder, PNG/JPEG checked by magic bytes, hex-only names, 50 MB cap, emptied at tray start) and the app names seen (for the mute switches). Logs carry the package and a key hash, never text. The phone acts only on keys it currently shows, through the apps' own intents; actions and records are rate-limited (10 actions/s; records paced at 40/s, a session over 200/s on arrival is closed) and size-limited. Toast arguments carry the phone id and notification key so toasts work after a restart; they stay in the user's own notification centre. A toast is only kept in step (and its clearing mirrored to the phone) once Windows has actually kept it. Toast XML escapes all text. Content is hidden while the PC is locked (default), always for notifications the app marks private, and kept off the lock screen (default); toasts that arrived while locked are filled in quietly at unlock. One-time codes copied on the PC are kept out of clipboard history and cloud clipboard, never synced back, and cleared after 60 s if unchanged. The Windows notification centre keeps shown toasts until they are cleared or the phone removes them (**implemented**; device tests pending) |
| 16 | Phone screen on the PC | Unwanted viewing or control of the phone | Paired PCs only, over the session transport (row 3). Each session needs the phone user's yes ("Always allow" is opt-in) and Android's own capture prompt, which Android shows every session. One consent covers the window's input for that session only. A sharing notification with Stop shows the whole time; Stop on the phone ends it, and the phone then declines that PC quietly for 30 s. After a dropped link the capture waits (paused) 30 s for the same PC only. Secure screens (banking, passwords) are captured as black by Android. Records are size-limited (4 MiB) and input is rate-limited like PC control (**implemented**; device tests pending) |
| 17 | Phone camera on the PC | Unwanted use of the camera; other users or programs reading the pictures; a replaced source DLL; leftovers on the PC | Paired PCs only, over the session transport (row 3). Each session needs the phone user's yes ("Always allow" is opt-in) plus Android's camera permission; Android's camera indicator and a notification with Stop show the whole time, and the service takes the `camera` type only while streaming. On the PC the camera ("Phone Bridge Camera") exists only while streaming: Session lifetime, Stop, Remove and Shutdown on every exit path, a sweep for leftovers at start-up and exit, and one UAC prompt each to install and to remove. The frames file lives in `%ProgramData%\PhoneBridge\camera` and is readable and writable only by SYSTEM, LocalService (Frame Server) and the installing user; it holds two frames and is zeroed at stop. The source DLL sits in a folder only administrators can write, with a versioned name. Like any webcam, apps of that Windows user can open the camera while it exists. Logs carry sizes, timings and HRESULTs, never pictures (**implemented**; device tests pending) |
| 18 | Phone audio on the PC | Hearing what the phone plays without the owner knowing; capturing a call or a protected app | Paired PCs only, over the session transport (row 3), started from the PC. The phone asks every session: Relay's own question (the only part the Settings switch "Share this phone's audio without asking" can remove) and then Android's screen-capture prompt, which no setting removes and which is single use. Apps that forbid capture (calls, some media apps) stay silent and Relay ends the session after about 2 seconds of silence with a message; it never falls back to the microphone. A notification with Stop shows the whole time (Android shows its cast indicator), Stop on either side or a lost link ends it, nothing resumes by itself. Audio travels as raw PCM in QUIC datagrams (an 8-byte header, then at most 64 KiB of whole samples), each checked before use; a malformed one ends the session. About 100 ms is buffered by the sender and 100 ms queued by the receiver, oldest dropped first, so a Wi-Fi stall leaves no backlog of old sound. The timeline and the logs keep who, which way and how long, never audio (**implemented**; device tests in the audio report) |
| 19 | PC audio on the phone | The PC playing sound on the phone, or capturing PC audio, unasked | Paired phones only. The PC asks its own user every session ("Play this PC's audio on <phone>?"), unless the user turned on "Play PC audio without asking" in Relay settings (off by default). The phone checks the format and that no PC audio session runs, then plays through its media output; it shows a notification with Stop, and Stop on either side or a lost link ends it. The PC captures only the default output device (loopback) and only while the session runs; the capture thread is stopped on every exit path, and pausing Relay ends it. Nothing is stored beyond who, which way and how long (**implemented**; device tests in the audio report) |
| 20 | Microphone | Silent recording of the phone's microphone | **Excluded by default and unreachable in this version.** The microphone is a separate mode (`source = 1`), never a fallback for playback capture. The phone would ask on every request with its own dialog that no setting skips, plus Android's RECORD_AUDIO grant, the microphone foreground-service type and Android's microphone indicator, with a "Microphone is being shared" notification and Stop. No PC UI sends this request, so the microphone cannot be started from the apps today; a request from a hand-made client still meets all of those gates (**implemented on the phone, not reachable from the apps**) |

## Known limitations found so far
- Relay metadata exposure (row 6) is inherent to any relay design.
- `pb --auto-accept` and the app's adb intent hooks skip or script the SAS decision; they are test-only and must not ship in release builds.
- Spike 1 used an unauthenticated test protocol on throw-away keys; it proves transport, not authorisation. Do not treat spike code as secure.
- The first GSO send failure on USB tethering (DECISIONS.md) is an availability bug, not a confidentiality one, but a flaky transport invites insecure retries; do not add silent fallbacks.

## Audio capture without Android's prompt (2026-11-04)
Both of these remove a protection Android normally gives, so both are the user's explicit choice, and Relay's notification with Stop is then the only sign of a share. The rule that the PC can only ask, and that the microphone asks every time, is unchanged.

**The hands-free grant.** If the user allows `PROJECT_MEDIA` for Relay outside the app, Android approves its capture prompt automatically, for audio and for screen sharing alike, with the capture icon still shown. Only a paired PC can request a capture, subject to Relay's own settings. Undone with `appops set ... PROJECT_MEDIA default`.

**The audio helper (debug builds only since v2 M2.1; release and qa builds carry none of its code or libraries, and remove an old install's adb identity and key once).** After its one-time setup:
- Relay holds a paired adb identity, which amounts to shell access to this phone. It is kept outside backups, encrypted under a key in Android's keystore, and used only for fixed commands. Anything that takes over Relay's process can use it: that is the main cost of this feature, and why it is off until the user sets it up after being told this.
- Relay holds `WRITE_SECURE_SETTINGS`, which covers far more than Wireless debugging. Same reasoning.
- While starting the helper, Wireless debugging is on for a few seconds, listening on the network and open to paired keys only. It goes back to how the user had it.
- The helper records everything routed to `REMOTE_SUBMIX`, including apps that opt out of capture, with no capture icon. Android routes media there; alarm, ringtone and notification sounds stayed on the speaker when measured.
- Any local app can reach the helper's loopback port. It gets a random nonce and nothing more without the secret (tested). Any app could also occupy the port first: the helper then can't start and Relay falls back, and Relay takes no audio from whatever holds the port, because it must prove the secret too.
- Other apps can't read the secret: it is in Relay's private storage and the shell's environment, and it never goes on a command line or in a log.
- A dead helper or Relay stops recording: recording exists only while Relay holds the connection. The helper exits when the APK it came from goes away.
- `libadb-android` has never had a security audit, and it runs in Relay's process during setup and starts.
- Turning the helper off stops it, revokes the grant when it can reach adb, and deletes the identity. The phone's Paired devices list still shows Relay until the user removes it, though the key is gone.

**Silencing the speaker.** The effect that silences the phone during a share needs no special access. Its risk is sound: if Relay dies, the speaker can play at the share's level until the service restarts and puts the volume back. Relay's notification stays the sign that a share is running.

## Rules that follow from this
1. No feature acts on a peer that is not in the paired-peer store.
2. Anything that reads from or controls the other device needs its own explicit, revocable permission.
3. All parsing of remote bytes is bounded and fuzzed before a feature ships.
4. No telemetry, no third-party services by default.

## Review findings fixed (2026-10-19)
- Exported `MainActivity` honoured test extras (`pair_code`, `confirm`) in release builds: any installed app could pair the phone with an attacker PC without the SAS check. Now only in debuggable builds.
- Unauthenticated LAN hosts could hold pairing connections open indefinitely: pairing ALPN refused unless a code is shown; handshake steps time-boxed (incoming QUIC handshake 5 s); at most 16 incoming connections in flight, and a paired peer's slot is released as soon as it is authenticated.
- Unpairing only blocked new connections: a removed device kept any session it had open (control, transfer). Now `unpair` closes its live connections at once.
- Discovery: a forged or stale candidate address no longer delays connects (candidates and saved addresses are dialled together) and is dropped after a failed dial; only the address the authenticated connection actually uses is saved. Dial-triggered probes at most every 30 s.
- PC -> phone control needs the accessibility service, plus either "Let my PC control this phone" or an approval on the phone for each request (30 s, no answer = deny). The phone shows who is in control and can end it at once (Stop, or turning the switch off).
- Android: allowBackup=false did not cover Android 12+ device-to-device transfer; data extraction rules now exclude everything.
- Tray pipe used the default DACL (other local accounts could connect): now this user (by SID, so an elevated tray still admits the user's unelevated "Send to") + SYSTEM only.
- Clipboard text no longer written to logs (tray.log, logcat).

## Mitigations added in v2, milestone M1 (2026-11-05)

Branch `cloud/v2-upgrade`; the rows above get their full update in milestone M11.

- **Share target:** nothing leaves the phone before the user confirms on a sheet naming the PC. On the PC, shared text waits for a Copy button unless "Copy shared text automatically" is on.
- **Consent prompts:**
  - Consent windows, the pairing-code comparison and the quick panel hide other apps' overlays and drop obscured touches.
  - The PC's remote input, including taps from its screen window, pauses while any prompt of Relay's is on screen.
- **Locked phone:**
  - No "always allow" path accepts on a locked phone: control, Instant screen, camera, audio, and the consent windows themselves.
  - Remote input pauses while the phone is locked.
- **Received files:**
  - Every received file is marked as from the internet (Zone.Identifier, ZoneId=3).
  - Risky types always ask, and shortcut types are refused by default.
- **Portable folder:**
  - `data\` is limited to the user, SYSTEM and Administrators.
  - The camera install refuses folders other accounts can change, and the camera DLL is embedded in Relay.exe.
  - DLLs load from System32 only; a CI check starts Relay.exe next to planted DLLs.
- **Release builds:**
  - Test-only switches (`--test-auto-accept`, `--test-audio-synth`, `relay-cli --auto-accept`) exist only with the `test-hooks` feature, and CI scans the exe for them.
  - Release APKs require the release key.
- **Fuzzing** (row 11, "planned"): ten cargo-fuzz targets for the parsers that read another device's or a stranger's input run on every push (`fuzz/`). The PC binary's settings and pipe parsers get randomized tests.

## Mitigations added in v2, milestone M2 (2026-11-05)

- **Audio helper (S5):** debug builds only. Release and qa builds carry no helper code, no libadb, Conscrypt or Bouncy Castle (CI checks the release graph), and delete an old install's adb identity, its Keystore key and the helper's settings once. The device-idle allow-list entry an old setup added can only be removed over adb.
- **Clipboard fingerprint (S9):** the last synced clip is stored as an HMAC-SHA256 under a Keystore key, not `String.hashCode()`, so a stored value no longer gives a short code away.
- **Single-instance pipe (S11):** named after the account's SID, so accounts with names in another script no longer share one pipe.
- **Privacy (S12):** PC toasts about text and links from the phone show only who sent them unless the user turns "Show shared text in notifications" on (Windows keeps toasts on disk); sensitive text is never shown. `tray.log` and Android's logcat lines about notifications carry no package names, and Android's logs moved from app-specific external storage to private storage.
- **"Open on phone" (A5):** when Android would block the app's screen, the phone shows a "Tap to open" notification and the PC is told so, instead of a false "ok".
- **Shared links (B3):** the address both devices open is exactly the one that was checked (trimmed, scheme in lower case, no spaces or control characters).

## Foundations in v2, milestone M3 (2026-11-06)

- **Keystore reset (B5):** when Android's keystore no longer opens Relay's sealed identity (its key was lost or replaced), that is a typed error, never a silent new identity: the phone stops retrying, shows "Relay can't open its keys", and offers "Reset and pair again" only after a confirmation that says each PC will see a new device. The reset deletes the identity, the Keystore key and the phone's allow lists, and keeps received files, the timeline and the logs. Only an unseal failure (bad tag, short blob, wrong seed size) leads there; any other start error keeps retrying. A PC keeps the old phone's pairing until the user removes it there: that entry can no longer authenticate, as the old key is gone.
- **Two PCs with one name (M3.3):** the phone's asks for Control, the screen and the camera are keyed on the PC's id, so a PC that copies a trusted PC's name still has to be allowed.
- **`devices.txt` (M3.4):** per-device facts on the PC are bounded when read and written (64 devices, 32 keys each, values cut at 256 characters; bad lines skipped), so a damaged or planted file can't grow memory without limit. It holds no secrets and grants nothing: trust stays in `peers.txt`.
- **Old peers (M3.1, M3.8):** the wire version stays 0 and the new `Hello` fields are optional, so a 0.2.0 build keeps working with the same pairing checks; capabilities only say what a peer can do and never skip a consent.

## Mitigations added in v2, milestone M4 (2026-11-06)

No change to the threat model. M4 adds design tokens, a code generator (`tools/gen-tokens`) that writes Rust, Kotlin and CSS, and a private Floot design project. It adds no parser, no network path and no permission, and the shipping apps only gain generated constants that are not used yet. The Floot project is a private preview that is never published, and its preview link (which carries a login-free token) is kept out of the repository.

## Mitigations added in v2, milestone M7 (2026-11-07)

- **Unlock gate (M7.1, M7.2, M7.3):** allow decisions, "always allow" and automatic accept, confirming a pairing, unpairing and turning the gate off ask for the phone's fingerprint or screen lock (API 30 and later: a strong biometric or the credential; API 29: weak or credential), and for Windows Hello on a Windows 11 PC, before they take effect. After a successful unlock nothing asks again for 60 s; a failed or cancelled unlock does nothing and starts no grace; locking the screen resets it. It is an extra step over a consent that still exists, so if the gate cannot run (no screen lock, no Hello, Windows 10, Remote Desktop) the action proceeds on the old consent dialog and the settings row says why: a person is never locked out of their own consent. "The PC can only ask" is unchanged: the gate never allows anything by itself. Residual risk: someone holding the unlocked phone or PC within the 60 s grace, or on a PC where Hello cannot run, skips the gate and still faces the consent dialog.
- **Disconnect everything (M7.4):** one action (tray menu, the phone's Settings) closes every connection (close code 410, the pairing is untouched), stops every share, turns every "always allow" off and pauses Relay until it is resumed. It asks nothing and needs no unlock because it only removes access.
- **Keyed discovery, PBD2 (M7.5, M7.6):** see row 4. A paired pair derives a key from its two identities; probes and answers carry a 16-byte HMAC over the exact packet, a replay cache that only authenticated packets enter, strict parsing (256 bytes, at most 6 addresses) and padding to at least 4 probes. A LAN host that holds no pairing cannot make a node dial an address of its choosing or learn which peers are paired. An attacker who floods PBD2 packets makes a node try up to 64 keys over 3 windows per packet; that is the same class as any UDP flood on the LAN.
- **Pairing limits (M7.7):** wrong tokens are counted per source (the remote IP: 3 in 10 minutes blocks that source) and all together (10 burn the code); the per-source count survives a code rotation, so rotating the code does not reset an attacker, and one source can block only itself. At most 2 pairing handshakes run at once, each cut off at 150 s. Residual risk: two devices behind one NAT share a source.
- **Per-peer quotas (M7.8):** see row 14.

## Mitigations added in v2, milestone M8 (2026-11-07)

- **Never is a refusal, not a grant.** A device set to Never gets its control, screen, camera and audio requests refused without a prompt. This removes a prompt and adds no access.
- **Per-device permissions limit what one paired device can do.** Before, a "yes" or an "Always" from one device applied to all; now a device that was not allowed asks (or is refused). A compromised or misbehaving paired device cannot use a permission the person gave to another.
- **Disconnect everything clears each device's Always and automatic accept.** Residual risk: Never answers and clipboard and notification switches are left in place, because they do not grant access to the screen, camera, audio or input.
- **Fresh devices start closed.** A device paired after the migration starts at Ask / off and never inherits an old global switch.
- **Residual risk:** until the PC reads the audio, clipboard and notification switches per device, those three are still all-devices on the PC.

## Mitigations and new surface in v2, milestones M9 to M11 (2026-11-08)

- **Partial files (M9.1, M9.2).** A receiver that loses the link keeps what arrived so the sender can continue. The partial lives in the data folder (private to the account), never in the save folder, under a name derived from the peer and a random 16-byte token the sender chose, never from the file name, so a file name cannot point outside the folder. A token only matches the peer that made it (`token_of_another_peer_never_matches`). Partials expire after 24 hours and are capped at 2 GiB per peer, 8 GiB in all and never below 256 MiB of free disk (`caps_hold_against_free_space`), oldest first, so a paired peer cannot fill the disk through them. A resume starts only if the receiver's kept bytes hash to the same prefix the sender holds; otherwise the receiver restarts at zero. The whole-file SHA-256 in `TransferDone` still covers every byte. A cancelled transfer deletes its partial. Residual risk: a paired peer can make the other side keep up to the caps above for 24 hours.
- **Send queue (M9.3).** Local only; no new message crosses the wire. At most 64 unfinished files per device. `queue.txt` holds file paths, names, sizes and resume tokens (percent-escaped, so a crafted name cannot add a line) in the account's data folder; after a restart every queue comes back paused and a file that moved shows "needs the file". The automatic retry fires only after the other device accepted and bytes flowed, so an unanswered or dismissed prompt is never offered again by itself. The PC can still only ask: a resumed offer goes through the same consent as a first one.
- **Clipboard history (M9.4).** Opt-in, off by default, 7 days, at most 200 clips of at most 64 KiB. A clip marked sensitive and a short run of digits (a one-time code) are never stored. On the PC each record is sealed with Windows DPAPI for the current user with an entropy value of its own (a history blob does not open as the identity seed and back); on the phone the module is built to use AES-256-GCM under a non-exportable Android Keystore key (the Keystore-backed cipher is not written yet: only a software key in the tests), with the version and the created time as authenticated data, so the time cannot be edited to dodge the expiry. A lost key makes the history read as empty and the file is deleted; turning the switch off deletes it. Search decrypts in memory only. Residual risk: anyone who can run code as the same Windows account, or on an unlocked phone as Relay, can read the history, as with the clipboard itself. Status: the storage modules are built and tested; the settings switch and the list are not yet on screen.
- **Drag and drop (M9.5, M9.6).** The PC sends dropped files through the same "Send to" choice as every other send, so with several phones the person picks the target. On a wide Android window a drop accepts only content from another app: never this app's files, a raw path or a link into the save folder's own tree. Residual risk: the same file reached through the media library (a `content://media/...` address) is not recognised as being in the save folder, so a person can drop a received file back; it cannot read the identity.
- **Update signing (M10.1).** A release manifest is trusted only if its Ed25519 signature (made offline by the owner) verifies over the exact bytes, it is at most 64 KiB, its artifact links start with the project's release address, its date is not older than the last accepted one or more than 7 days ahead, and its version is not older than the last seen. A rolled-back or replayed manifest is refused; a key can be replaced only by a successor the current key signed. Design: the check never installs anything, it opens the release page. Status: only the verifier and the signing tool exist; no part of the PC or phone app calls them yet and no public key is embedded, so today there is no update check at all. Once wired, every manifest is refused as `UnknownKey` until the owner provides a key. Residual risk: whoever holds the signing key can offer a release; a compromised key is replaced by the next-key chain only if the old key signed it first.
- **Installer firewall rule (M10.4).** The installer adds one inbound rule for `Relay.exe`, UDP only, Private profile only, and only when run as an administrator (a rule needs one); it never opens Public or Domain networks and the uninstaller removes it. A per-user install adds no rule and Windows asks once instead. Residual risk: on a Private network any device on that network can reach Relay's port, as before; pairing and the paired-peer check still decide who is served.
- **Release signing and publishing (M10.3, M10.9).** The signing step reads its certificate from secrets by name, is skipped without them and never runs for pull requests; the package publisher is split so the job that downloads release files cannot write packages and the job that writes packages runs nothing from the release.

**Get phone clipboard (PC asks the phone for what it copied).** Ctrl+Alt+V or `--pull-clipboard` on the PC sends `ClipboardPull` to the default phone. The phone answers only if its per-PC "Share the clipboard" switch for that PC is on, the screen is on and unlocked, and Relay may open a window from the background ("Display over other apps"); the answer is one clipboard (text, or a picture if both sides share pictures). Otherwise it says why, in words, and sends nothing. The PC cannot read the phone's clipboard any other way, cannot ask while the phone is locked, and a PC that is not paired or whose switch is off gets a refusal. No accessibility service, developer option or debug permission is used; Android 12+ may show "Relay pasted from your clipboard" on the phone.

**Deferred clipboard delivery (CP1.3).** The latest already-admitted incoming clipboard payload may remain in the running tray process's RAM while the PC is locked or another process holds the clipboard. It is replaced by a newer received clip, cleared after a successful write or permanent error, and superseded by a newer local copy. Received images and their conversion buffers remain memory-only. Sensitive/history exclusion markers are retained; turning history off while waiting can only tighten them. No clipboard text is logged. Device lock/unlock behavior still needs the owner's live device check.

**Clipboard text echo expiry (CP1.4).** The phone-side echo guard keeps only a hash and monotonic arrival time in RAM and blocks a matching remote clip for 15 seconds. It prevents immediate ping-pong while allowing a later deliberate re-copy; sharing and private-content switches are still required.

**Inline shared text (CP1.8).** Text/link offers from authenticated paired devices do not invoke file-save or Windows Hello file consent. Clipboard replacement still requires the toast's Copy action unless the owner opted into automatic shared-text copy; link opening still requires a click. Default-off auto-copy and clipboard history controls are unchanged. File and image admission policies are not bypassed.

Clipboard per-device enforcement (2026-11-11): the Windows per-phone clipboard grant is checked for outgoing/incoming sync and explicit clipboard sends/pulls; an explicit text action bypasses only the global background-sync switch. Received clips waiting in RAM recheck the grant, pause and image/auto-copy policy before every actual write, discarding revoked copies. Share-sheet Text/Link remains governed by separate explicit Copy/Open consent. The phone rechecks a requesting PC before a focus read. Enabling sharing offers the existing overlay permission page, never grants it; new-device defaults remain off. No automatic pulls are shipped by these repairs.

### Automatic clipboard pull (plain Ctrl+V)
When the user comes back to the PC after at least 30 s without keyboard or mouse input (Windows `GetLastInputInfo`, which reports that input happened, never which keys; no input hook), a PC with Share clipboard on asks its default phone for the clipboard (`ClipboardPull` with `auto`). **A paired PC with the per-phone switch on can therefore read the phone's clipboard without a key press whenever the phone's screen is on and unlocked.** What limits it: the per-phone switch and Share clipboard on both devices (both off by default), the phone's screen must be on and unlocked, "Display over other apps" must be allowed, the phone sends only a clip that is new and newer than the PC's own copy, text marked private is not sent without the Passwords and codes switch, pictures need Share images on both, and at most one request every 5 s. A payment app that refuses overlay windows gives the reader no focus, so the phone cannot read while it is in front. Android shows its own "pasted from your clipboard" message once per new clip.
