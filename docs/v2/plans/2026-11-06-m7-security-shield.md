# M7 Security shield Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:executing-plans (inline, TDD, one reviewer at the end of the milestone). Steps use checkbox (`- [ ]`) syntax. Run `advisor` where a step says **ADVISOR** (M7.3, M7.5, M7.6 and the `.R` task are security or wire changes). Run several Monitors at once (cargo, gradle, CI by full SHA, fuzz); never wait on one job alone.

**Goal:** add an unlock gate (BiometricPrompt on Android, Windows Hello on the PC) in front of sensitive decisions, a "Disconnect everything" action, keyed discovery (PBD2), per-source pairing limits and per-peer session and offer quotas, without breaking Relay 0.2.0 peers.

**Architecture:** pure functions decide gate behaviour, grace windows, limits and quotas (plain tests on Linux); platform code (BiometricPrompt, Windows Hello interop, the QUIC node) only calls them. The PBD2 key is derived inside `pb-identity`, which alone holds the secret key, and MACs are computed in the transport.

**Tech Stack:** Rust 1.99.1 (`ed25519-dalek` 2.2, `curve25519-dalek` 4.1, `sha2` 0.10, new `hkdf`/`hmac` 0.12), iroh QUIC, `windows` 0.62, Kotlin, androidx.biometric and fragment.

**Spec:** `docs/v2/SPEC.md` lines 291–316 (plus 36–37, 48–51, 77–80); rows M7.1–M7.R in `docs/v2/PROGRESS.md`; `docs/THREAT_MODEL.md` rows 4 and 14; `docs/WIRE_PROTOCOL.md`.

## Review Focus
1. **No biometric enrolled but a PIN set:** the gate works with the PIN (device credential). With no screen lock it cannot be turned on. Tests: `cannot_enable_without_a_screen_lock`, `api29_uses_weak_or_credential` (M7.1).
2. **Lockout or a busy verifier never bypasses the gate:** five failed attempts (`ERROR_LOCKOUT` / `ERROR_LOCKOUT_PERMANENT` on Android) or a busy prompt (`HelloState::DeviceBusy` on Windows) is a hard failure (`GateResult::Failed` / `GateStep::Prompt`), never an `Unavailable` fallback. Tests: `biometric_lockout_maps_to_failed_never_unavailable`, `hello_device_busy_still_requires_the_gate` (M7.1, M7.2).
3. **A Relay 0.2.0 peer on the LAN:** still found by PBD1 and still talks. Tests: `a_peer_without_discovery2_is_still_found_by_pbd1`, `a_0_2_0_peer_still_talks` (M7.6).
4. **A replayed, forged or bogus-IP PBD2 answer:** never dialled. Tests: `a_replayed_probe_is_ignored`, `a_tampered_address_fails_the_mac`, `an_answer_offers_only_its_maced_addresses`, `loopback_and_multicast_candidates_are_rejected` (M7.6).
5. **A flood of pairing attempts from one machine while the owner pairs from another:** the owner still pairs, as long as the attacker has fewer sources than the global cap; at the global cap the code burns, the tray rotates to a new one and the owner scans that (an attacker with many sources can still slow pairing, but cannot pair). Tests: `another_source_can_still_pair`, `a_pairing_slot_frees_after_its_time_box`, `the_source_table_stays_bounded`, `ipv6_sources_share_their_slash_64` (M7.7).
6. **A paired but misbehaving device opening sessions in a loop or offering many large files:** refused (with overflow-safe byte math across peers), other devices unaffected; and a normal user sharing 50 photos at once is never refused (the Android share sheet sends files one after another, each on a fresh session, `EntryPoints.kt:151`). Tests: `the_seventeenth_session_is_refused`, `in_flight_offers_count_against_free_space`, `overflow_offer_size_is_refused_without_panic`, `other_peers_are_not_affected`, `sharing_fifty_files_at_once_is_not_refused` (M7.8).

## Rulings already made
- Ruling: "Disconnect everything" also turns auto-accept off — the SPEC says it turns every "always allow" off and auto-accept (default on on the PC) saves files without asking — cost if wrong: the user re-enables auto-accept after resuming.
- Ruling: quotas count concurrency, not rate — `MAX_SESSIONS_PER_PEER = 16`, `MAX_OFFERS_IN_FLIGHT_PER_PEER = 16`, and a flood cap `MAX_OFFERS_PER_PEER_PER_MIN = 600` — the share sheet and `--send` send many files in sequence on fresh sessions, so a small per-minute cap would refuse normal use — cost if wrong: a very fast scripted client is slowed; M7.8 Step 0 re-reads the send paths and may raise the numbers.
- Ruling: pairing sources key on the IPv4 address or the IPv6 /64, and the per-source table holds at most 256 entries (oldest evicted) — one machine can rotate addresses inside its /64 and the table must not grow without bound — cost if wrong: two neighbours in one /64 share a budget.
- Ruling: with the gate on but no screen lock (first start, or the lock is removed later), the gate counts as unavailable with a reason and actions fall back to today's confirmation, like the PC — the phone cannot prompt without a credential — cost if wrong: none beyond the extra step being absent.
- Ruling: credential lockout (`ERROR_LOCKOUT`, `ERROR_LOCKOUT_PERMANENT`) and `HelloState::DeviceBusy` are treated as active gate failures (`Failed`), never as `Unavailable` — otherwise an attacker could fail five times on purpose, or trigger a concurrent prompt, to reach the `ProceedNoGate` fallback — none.
- Ruling: pairing limits key on the remote IP — the pairing source is unknown before TLS completes and the joiner's key is chosen by the attacker, so a per-key limit is useless — cost if wrong: users behind one NAT share a budget of 3 bad tokens per 10 min.
- Ruling: the per-peer `discovery2` flag lives in a new file `discovery2.txt`, never as a 4th `peers.txt` field — 0.2.0 rejects a 4th field and would lose the pairing on downgrade — cost if wrong: one more small file.
- Ruling: `reserved_capabilities_are_not_advertised_yet` changes so only `resume` stays reserved — `discovery2` now ships, as M3.2 said it would — this is not a weakened test — none.
- Ruling: if the gate is on but genuinely unconfigured in the environment (`OldWindows`, `RemoteDesktop`, `NotConfigured`, `DisabledByPolicy`, `NoScreenLock`), the action falls back to today's confirmation and the dialog says why — the gate is an extra step over a consent that still exists; locking the user out of their own consent is worse — cost if wrong: an attacker in a Remote Desktop session skips the gate but still faces the consent dialog.
- Ruling: "Disconnect everything" has no confirmation and no gate — it only removes access — cost if wrong: an accidental tap pauses Relay until resumed.
- Ruling: `wrong_tokens_burn_the_code_after_three_attempts` is replaced by the new per-source tests — the spec changes the rule; the new tests are strictly more specific — none.

### Task M7.6: PBD2 packets (wire change)
**Files:** `crates/pb-transport/src/discovery.rs`, new `crates/pb-transport/src/discovery2.rs`, `crates/pb-protocol/src/lib.rs`, `docs/WIRE_PROTOCOL.md` (a new "Discovery" section that also documents PBD1), `docs/THREAT_MODEL.md` (row 4), `fuzz/fuzz_targets/discovery2_packet.rs` and its `[[bin]]` in `fuzz/Cargo.toml`.
**Packet format** (written into WIRE_PROTOCOL.md): Probe (39 bytes) = `"PBD2" | kind=1 u8 | quic port u16 LE | nonce[16] | mac[16]`, mac = `k.mac(["probe", window u64 LE, nonce, port LE])`. Answer = `"PBD2" | kind=2 | port u16 LE | probe_nonce[16] | own_nonce[16] | n u8 (≤ 6) | n × (family u8 4|6, ip 4|16 bytes, port u16 LE) | mac[16]`, mac = `k.mac(["answer", window, probe_nonce, own_nonce, port, &[n], addr bytes])`. Maximum length 4+1+2+16+16+1+6×19+16 = 170 bytes; the receive buffer goes from 64 to 256 bytes; anything longer, or with n > 6, is dropped.
**Behaviour.** Sending: one probe per stored peer marked `discovery2`, plus random-MAC dummy probes until there are at least 4; PBD1 probes are still sent while any stored peer is not marked `discovery2`; nonces from `getrandom`. Receiving: for each `discovery2` peer try windows −1, 0, +1 with per-peer keys cached in a `HashMap<PeerId, DiscoveryKey>` invalidated on pin or unpin, verified through `k.verify(...)`; drop a `(peer, nonce)` seen in the last 2 windows (LRU of at most 1024); answer at most once per peer per second; only MACed addresses in an answer that pass `valid_candidate_ip(ip)` (not unspecified, loopback, multicast, or broadcast `255.255.255.255`) become candidates, never `from.ip()` unless it is in the list; PBD1 packets whose tag matches a `discovery2` peer are ignored. The per-peer flag lives in `discovery2.txt` in the data dir (hex ids, one per line, at most 64 lines, written atomically like `peers.txt`); a peer is marked when a session's `Hello::supports(CAP_DISCOVERY2)` is true; unpairing removes it. `local_capabilities()` adds `CAP_DISCOVERY2` and `reserved_capabilities_are_not_advertised_yet` is updated so only `resume` stays reserved (see the ruling).
