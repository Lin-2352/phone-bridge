# Relay: review findings (2026-11-04)

These are findings only; nothing here is fixed yet. Nothing was built, run or tested on a device for this review. Line numbers refer to commit `456e480` (main on 2026-11-04).

## Context
- Asked for: bugs, improvement scope, real-life quality-of-life (QoL) gaps, security vulnerabilities, restrictions on newer Android (14–17) that don't exist on the Android 13 test phone, plus any other kinds of problem not mentioned.
- Method: read the docs (README, CHANGELOG known issues, THREAT_MODEL, WIRE_PROTOCOL, DECISIONS) and the code (Android app, pb-transport, pb-ffi, pb-tray, pb-identity). Checked Android platform changes against current Android docs and press reports (sources at the end). Nothing was built, run or tested on a device. Items marked *(verify)* need a device check.
- Already-known issues in [CHANGELOG.md](../CHANGELOG.md) / README are **not** repeated unless there's something new to add.
- **The main reason for the Android gap:** [build.gradle.kts:22](../android/app/build.gradle.kts#L22) sets `targetSdk = 36`, so every rule tied to *target* SDK 34–36 already applies. But the only test phone runs Android 13, so rules tied to the phone's *Android version* (14, 15, 15 QPR1, 16, 17) have never run.

## 1. Security vulnerabilities

| S1 | **Cross-device clipboard and file injection.** `ShareActivity` is exported with no confirmation. Any foreground app can send `ACTION_SEND`+`EXTRA_TEXT` (or streams) and Relay sends it at once. On the PC, `auto_accept` is on by default ([settings.rs:81](../crates/pb-tray/src/settings.rs#L81)), and a `Text` offer always goes to the clipboard through `UiEvent::Clipboard` → `set_clipboard_own(...,false)`. That path ignores the "Share clipboard" switch and `keep_in_history`, so it also lands in Win+V history and cloud clipboard. | [AndroidManifest.xml:70](../android/app/src/main/AndroidManifest.xml#L70), [EntryPoints.kt:24-136](../android/app/src/main/java/dev/phonebridge/app/EntryPoints.kt#L24-L136), [core.rs:1646-1661](../crates/pb-tray/src/core.rs#L1646-L1661), [ui.rs:1191-1206](../crates/pb-tray/src/ui.rs#L1191-L1206) | Clipper malware (swapping crypto addresses, or a command the user is about to paste into a shell) and file staging on the PC. Direction: confirm sheet unless launched through the system chooser; PC-side switch for text→clipboard; respect `keep_in_history`. Repro: `adb shell am start -n dev.phonebridge.app/.ShareActivity -a android.intent.action.SEND -t text/plain --es android.intent.extra.TEXT pwned` |

## 4. Real-life QoL
- **Exact version match + no update notice**: after updating one side, everything fails with "update both" (close code 426). Add an opt-in GitHub Releases check, or tolerate minor-version differences ([lib.rs:1059-1063](../crates/pb-transport/src/lib.rs#L1059-L1063)).
- **Accessibility switched off after every session** ([ControlService.kt:187-195](../android/app/src/main/java/dev/phonebridge/app/ControlService.kt#L187-L195)): combined with restricted settings and OEM countdown warnings, each Control session means a trip into Settings. Make it optional and explain why. Add S4's unlock check before making it optional.
- **"Always allow" still needs a tap.** For the camera, unless the overlay permission is granted (background activity launch rules). For the screen, Android's own capture prompt still shows on every share ([ScreenConsentActivity.kt:78-81](../android/app/src/main/java/dev/phonebridge/app/ScreenConsentActivity.kt#L78-L81), [ScreenConsentActivity.kt:122](../android/app/src/main/java/dev/phonebridge/app/ScreenConsentActivity.kt#L122)), unless Instant screen or the PROJECT_MEDIA grant is used. The UI should say so.
- Device names fixed to `Build.MODEL` / `COMPUTERNAME`; allow renaming. One-PC limit is known.
- Naming drift: phone saves to `Downloads/Relay`, PC to `Downloads\Phone Bridge`; `%LOCALAPPDATA%\PhoneBridge`; "Phone Bridge Camera".
- Windows Firewall: new networks default to Public, which blocks inbound. Detect it and guide the user (DECISIONS Phase 1 noted the need for a scoped rule).
- "Open on phone" reports success when Android blocked it (A5). One-time-code detection is English-only ([notify.rs:21-30](../crates/pb-transport/src/notify.rs#L21-L30)). All UI strings are hard-coded English in Kotlin and Rust, with no localization.
- OEM background killers (Xiaomi autostart, Samsung deep sleep, Huawei): add per-OEM onboarding beyond the battery-exemption row.
- LAN only (relay disabled): no use from mobile data or another network. An optional self-hosted relay would fit the threat model.

## 5. Improvement scope (engineering)
- Events identify peers by **name**, and allow-lists map name→id (`uniquePeerId`). Duplicate or renamed PCs break "always allow". Carry the peer id in `PbEvent`.
- **Idle wakeups contradict "stay light"**: `AppLog.sampleLoop` runs every 10 s with the screen on and 60 s with it off, all day ([AppLog.kt:206-220](../android/app/src/main/java/dev/phonebridge/app/AppLog.kt#L206-L220)). The status redraw every 60 s while the PC is away re-posts the service notification, the tile and a Glance widget session ([PbService.kt:268-273](../android/app/src/main/java/dev/phonebridge/app/PbService.kt#L268-L273), [PbService.kt:985-992](../android/app/src/main/java/dev/phonebridge/app/PbService.kt#L985-L992)).
- Per-frame `ByteArray` allocation in the screen encoder at 60 fps ([ScreenShare.kt:368](../android/app/src/main/java/dev/phonebridge/app/ScreenShare.kt#L368)).
- Discovery is IPv4 broadcast only; many phones filter broadcasts while dozing. Consider mDNS/NSD, which also fits Android 17's device-picker route.
- Dormant helper: remove it or put it behind a build flavor.

## 6. Other categories you didn't list
- **Release / supply chain**: the release APK falls back to the debug key ([build.gradle.kts:10-13](../android/app/build.gradle.kts#L10-L13), [build.gradle.kts:45](../android/app/build.gradle.kts#L45)), which breaks updates (signature mismatch). CI builds no APK, runs no R8 build and no Android unit tests (the R8 crash in DECISIONS Phase 8b proves the gap). Actions are pinned to tags, and `dtolnay/rust-toolchain@master` is a moving ref ([ci.yml](../.github/workflows/ci.yml)), and the release publisher runs `oras-project/setup-oras@v1`, pinned only to a tag, with `packages: write` ([publish-package.yml](../.github/workflows/publish-package.yml#L17-L27)). Windows binaries are unsigned (SmartScreen, and Smart App Control can block them outright). No SBOM or reproducible builds ([THREAT_MODEL.md](THREAT_MODEL.md) row 13 "planned").
- **Licensing compliance**: no third-party notices in the APK or PC app (Apache-2.0 NOTICE terms, BSD/MIT crates, the scrcpy-derived helper code).
- **Platform coverage**: no Windows ARM64 build (the x64 camera DLL likely can't load into an ARM64 Frame Server *(verify)*); no `armeabi-v7a` APK (low-end and Go phones).
- **Docs drift**: [THREAT_MODEL.md](THREAT_MODEL.md) row 10 and DECISIONS Q4 rely on `play`/`foss` flavors that don't exist (the accessibility service ships in every build). Row 16 says Android prompts every session, but Instant screen skips it. Row 18 says raw PCM, but the phone sends Opus.
- **Testing**: one phone (Android 13, ColorOS) and one PC. The fuzzing harness is still "planned" ([THREAT_MODEL.md](THREAT_MODEL.md) row 11).

## Verification (how to confirm, if/when you act)
1. Android 16 emulator or Pixel (15 QPR1+): start an audio share and the mirror, lock the phone. Expect A1/B2.
2. Android 15+: post an SMS or app notification with a code. Expect a redacted text on the PC (A2).
3. Install the APK through a browser on Android 13+, then try to enable Relay Control and Notification access (A3).
4. S1 repro: the adb `am start` command in S1. Watch the PC clipboard and Win+V history.
5. Android 14+: choose "single app" in the capture prompt; check video and click mapping (A4).
6. Android 17: `adb shell cmd audio set-enable-hardening enable`, then force-stop mid-share and check the volume (A8). Build once with targetSdk 37 to see A9.
7. Send a 2–4 GB file to the phone, then request Control from the PC during the MediaStore copy (B1).
